# Конспект: конкурентность в Python

> Это мой конспект теории, разобранной в ходе проекта. Каждое утверждение
> по возможности подкреплено экспериментом из `experiments/`.

## 1. Процесс, поток, корутина

| | Процесс | Поток (thread) | Корутина (asyncio) |
|---|---|---|---|
| Что это | Экземпляр программы с **собственной памятью** | Поток исполнения **внутри** процесса, память общая | Функция, которая умеет **приостанавливаться** на `await` |
| Кто переключает | ОС | ОС (+ GIL в CPython) | Сам код, в точках `await` |
| Тип многозадачности | вытесняющая | вытесняющая | **кооперативная** |
| Общая память | нет (нужны pipe/queue/shared memory) | да | да (один поток) |
| Стоимость создания | десятки мс, МБ памяти | ~0.1 мс, ~15 КБ RSS (exp05) | мкс, <1 КБ (exp05) |
| Реальный параллелизм на CPU | **да** | в CPython с GIL — **нет** для Python-кода | **нет** (один поток) |
| Типичное применение | CPU-bound на чистом Python | блокирующий I/O, C-библиотеки без GIL | много одновременного I/O (сеть) |

**Вытесняющая** многозадачность: тебя могут прервать в любой момент — ты не
контролируешь, где. **Кооперативная**: задача сама отдаёт управление
(`await`). Отсюда главное различие в гонках данных (exp04).

## 2. Конкурентность ≠ параллелизм

- **Конкурентность** (concurrency) — несколько задач *в процессе выполнения*
  одновременно; они могут чередоваться на одном ядре. Это про *структуру*.
- **Параллелизм** (parallelism) — задачи *физически выполняются* в один момент
  на разных ядрах. Это про *исполнение*.

asyncio — конкурентность без параллелизма. multiprocessing — параллелизм.
Потоки в CPython с GIL — конкурентность, а параллелизм только пока GIL отпущен
(I/O, C-код).

## 3. I/O-bound vs CPU-bound

- **I/O-bound**: время уходит на *ожидание* (сеть, диск, БД). CPU простаивает.
  Признак: wall time ≫ CPU time. В exp01 последовательный прогон: 5.2 с wall
  и 0.15 с CPU — процесс 97% времени ждёт.
- **CPU-bound**: время уходит на вычисления. Признак: wall ≈ CPU time.

Сначала определи тип нагрузки, потом выбирай инструмент. Профилируй, не угадывай.

## 4. GIL (Global Interpreter Lock)

**Что это.** Мьютекс в CPython: в каждый момент байткод Python исполняет
только один поток процесса.

**Зачем он.** Управление памятью CPython основано на подсчёте ссылок
(`refcount`). Без GIL каждое изменение счётчика пришлось бы защищать
отдельно — медленнее для однопоточного кода и сложнее для C-расширений.
GIL — простое глобальное решение.

**Когда GIL отпускается:**
- блокирующий I/O (`socket.recv`, `file.read`, `time.sleep`);
- многие C-расширения на время тяжёлой работы: `hashlib`, `zlib`, NumPy,
  PyTorch и др. (exp02, часть B: потоки дают ×1.96 на 2 ядрах);
- принудительно раз в `sys.getswitchinterval()` (по умолчанию 5 мс) —
  чтобы один поток не захватил процессор навсегда.

**Следствия:**
- Потоки **не ускоряют** чистый Python-код на CPU (exp02 A: ×0.86 — даже медленнее
  из-за борьбы за GIL).
- Потоки **ускоряют** I/O и C-код, отпускающий GIL.
- GIL **не защищает** твой код от гонок (exp04): он делает атомарными отдельные
  операции интерпретатора, но не твою последовательность «прочитать → изменить → записать».

**Будущее.** PEP 703: free-threaded CPython. В 3.13 — экспериментальная сборка
`python3.13t`, в 3.14 — официально поддерживаемая (PEP 779), но пока не по
умолчанию. Однопоточный код в ней немного медленнее, а часть C-расширений ещё
не готова.

## 5. Как работает asyncio

1. **Корутина** — объект, созданный вызовом `async def`-функции. Сам по себе
   он ничего не делает, пока его не запустят.
2. **Event loop** — бесконечный цикл в одном потоке: берёт готовые к работе
   задачи, выполняет каждую до ближайшего `await`, где она ждёт I/O.
3. Под капотом loop использует системный механизм ожидания событий на множестве
   сокетов: `epoll` (Linux), `kqueue` (macOS), IOCP (Windows). Одним системным
   вызовом loop узнаёт, какие из тысяч соединений готовы.
4. **Task** (`asyncio.create_task`) — обёртка, которая ставит корутину в
   расписание loop'а. Без неё `await coro()` выполняет корутины последовательно.

**Главное правило asyncio:** никакого блокирующего кода в корутинах. Один
`time.sleep(0.3)` или `requests.get()` замораживает **всех** (exp03: опоздание
891 мс вместо 10 мс). Решения:
- асинхронная библиотека (`httpx.AsyncClient`, `asyncpg`, `aiofiles`);
- блокирующий I/O → `await asyncio.to_thread(fn)`;
- тяжёлый CPU → `loop.run_in_executor(ProcessPoolExecutor(), fn)`.

**Ограничивай конкурентность** (`asyncio.Semaphore`), иначе 100 000 задач откроют
100 000 соединений.

**Структурная конкурентность** (`asyncio.TaskGroup`, 3.11+): если одна задача
упала, остальные отменяются. `gather` по умолчанию оставляет их висеть.

## 6. Гонки данных и синхронизация

**Race condition** — результат зависит от порядка выполнения. Классика:
**lost update** (`x += 1` из нескольких потоков) и **check-then-act**
(«проверил баланс → списал»).

| Примитив | Для чего |
|---|---|
| `Lock` | взаимное исключение: один владелец критической секции |
| `RLock` | тот же поток может захватить повторно (рекурсия) |
| `Semaphore(n)` | не больше n одновременно (пул соединений, rate limit) |
| `Event` | «сигнал»: одни ждут, другой сообщает |
| `Condition` | ждать выполнения условия под локом |
| `Queue` | потокобезопасная очередь — лучший способ **не делить** состояние |
| `Barrier` | все ждут, пока соберутся n участников |

У asyncio свои версии (`asyncio.Lock`, `asyncio.Queue`, ...). `threading.Lock`
в корутине заблокирует весь event loop.

**Лучшая синхронизация — отсутствие общего изменяемого состояния:** передавай
данные через очереди (producer–consumer), используй неизменяемые объекты.

**Deadlock** — циклическое ожидание: T1 держит A и ждёт B, T2 держит B и ждёт A.
Четыре условия Коффмана: взаимное исключение, удержание и ожидание, отсутствие
вытеснения, циклическое ожидание. Убери любое — deadlock невозможен. Проще всего
убрать цикл: **единый глобальный порядок захвата локов** (exp04, часть 3).

## 7. multiprocessing: что важно знать

- **fork vs spawn.** `fork` (Linux по умолчанию до 3.14) копирует процесс
  целиком — быстро, но опасно с потоками (копируются захваченные локи).
  `spawn` (Windows, macOS, а в 3.14 и Linux перешёл на `forkserver`) запускает
  чистый интерпретатор и **заново импортирует модуль** → обязательна охрана
  `if __name__ == "__main__":`.
- Данные между процессами передаются через **pickle** — это копирование и
  сериализация. Большие массивы так гонять дорого (выход: `shared_memory`,
  memmap-файлы, или передавать путь, а не данные).
- Функции для пула должны быть **на верхнем уровне модуля** (lambda не пиклится).

## 8. Как выбирать — шпаргалка

```
Нагрузка I/O-bound?
├── да → много одновременных операций (сотни+), есть async-библиотеки?
│        ├── да → asyncio
│        └── нет / мало операций / легаси-код → ThreadPoolExecutor
└── нет (CPU-bound)
         ├── тяжёлая работа в NumPy/PyTorch/C, отпускающем GIL → потоки уже помогут
         ├── чистый Python → ProcessPoolExecutor (или переписать на NumPy/Numba/Cython)
         └── очень большой масштаб → распределённо (Ray, Dask, Spark)
```

## 9. Связь с ML

- `torch.utils.data.DataLoader(num_workers=N)` — это **процессы**: декодирование
  картинок и аугментации на Python упираются в GIL.
- Онлайн-инференс за веб-сервисом (FastAPI) — это **asyncio**: модель вызывается
  в отдельном пуле, чтобы не блокировать loop (exp03).
- Сбор данных из API / скрапинг — **asyncio** с семафором и retry.
- NumPy/PyTorch внутри отпускают GIL, поэтому многопоточность в них работает.
