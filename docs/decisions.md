# Decisions log — почему сделано именно так

Каждое решение: что выбрал → какие были альтернативы → почему.

| # | Решение | Альтернативы | Почему |
|---|---|---|---|
| 1 | **Локальный тестовый сервер** с параметром `?delay=` | Реальные сайты; публичный httpbin | Воспроизводимость (нет сетевого шума), известный теоретический минимум, не нагружаем чужие сервисы |
| 2 | Сервер на **«голом» asyncio** | aiohttp, FastAPI + uvicorn | Ноль зависимостей; сам сервер — наглядный пример asyncio (один поток держит сотни соединений) |
| 3 | Сервер в **отдельном процессе** | Поток внутри клиента | Иначе сервер и клиент делят один GIL, и мы меряем их взаимное влияние |
| 4 | **httpx** как клиент | `requests` + `aiohttp` | Одна библиотека с одинаковым sync и async API: сравниваем модель исполнения, а не две разные библиотеки |
| 5 | **Одинаковые уровни конкурентности** (1, 4, 16, 64, 100) для потоков и asyncio | Подобрать «лучшее» для каждого | Честное сравнение при равных условиях |
| 6 | **3 повтора, mean ± std** | Один запуск | Один замер — шум. Различия меньше std не считаем значимыми |
| 7 | `time.perf_counter()` + `time.process_time()` | `time.time()` | perf_counter монотонный и точный; CPU-время показывает, ждёт процесс или считает |
| 8 | **Speedup** вместо секунд в CPU-эксперименте | Абсолютное время | Безразмерная величина, сравнима между машинами |
| 9 | Две CPU-нагрузки: **чистый Python и hashlib** | Только одна | Проверяем распространённый миф «потоки бесполезны для CPU»: верно только для кода, держащего GIL |
| 10 | `concurrent.futures` (пулы) | Голые `Thread`/`Process` | Ограничение числа воркеров, переиспользование, исключения возвращаются в вызывающий код |
| 11 | `asyncio.TaskGroup` | `asyncio.gather` | Структурная конкурентность: ошибка одной задачи отменяет остальные |
| 12 | `asyncio.Semaphore` для лимита | Без лимита | Без лимита 100 000 задач = 100 000 соединений; в проде лимит обязателен |
| 13 | **Пульсометр event loop** (exp03) | Мерить только общее время | Общее время не показывает главное: сколько ждали ДРУГИЕ клиенты, пока loop был занят |
| 14 | Данные в **JSON**, графики **отдельным скриптом** | Рисовать сразу в эксперименте | Данные — первичны; график можно перестроить без многоминутных замеров |
| 15 | **src-layout** (`src/concurrency_lab/`) | Пакет в корне | Тесты импортируют установленный пакет, а не случайно лежащие рядом файлы; стандарт сообщества |
| 16 | **Тесты на корректность** | Только бенчмарки | Быстрый, но неверный код бессмысленно сравнивать; тесты гарантируют, что все варианты делают одну работу |

## Что пересмотрено по ходу исследования

- **Клиент в каждом потоке → общий клиент.** Первая версия давала каждому потоку
  свой `httpx.Client` (thread-local), чтобы «избежать конкуренции». Замеры
  показали аномалию: при 64 потоках стало медленнее, чем при 16, а CPU-время
  оказалось в 33 раза больше, чем с общим клиентом. Диагностика: `httpx.Client()` стоит ~50 мс CPU (загрузка
  CA-сертификатов в SSL-контекст). Решение: один клиент на все потоки. Оба
  варианта оставлены в эксперименте как урок.
- **Процессы: `httpx.get()` на запрос → клиент на процесс.** Та же причина: новый
  клиент и TCP-соединение на каждый запрос. После исправления процессы с 2
  воркерами ускорились вдвое (5.4 с → 2.7 с).
- **Демонстрация гонки `x += 1`.** На CPython 3.13 с GIL гонка не проявилась даже
  при `switchinterval=1e-6`. Причина: интерпретатор отдаёт GIL только в
  определённых точках (вызовы функций, переходы назад), а внутри `+=` их нет.
  Добавлен вариант с вызовом функции между чтением и записью — потеря 44% обновлений.
